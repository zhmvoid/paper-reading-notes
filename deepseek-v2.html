01 · Executive Summary

一句话总结

DeepSeek-V2 用两种不同层面的稀疏化解决两类成本：MLA 将每个 token 的多头 Key/Value 压缩成共享 latent cache，降低长上下文推理的 KV 存储与访存成本；DeepSeekMoE 将 FFN 拆成大量细粒度专家，只激活少量专家，并用设备受限路由与三类辅助损失控制 EP 通信和负载不均。

236B总参数量
21B每 token 激活参数
93.3%相对 DeepSeek 67B 的 KV Cache 降幅
5.76×最大生成吞吐提升（论文报告）
最重要的阅读主线：先理解 $c^{KV}$ 如何产生，再推导 $W^{UK}$ 为什么能左移到 Query 路径，最后理解为什么 RoPE 必须解耦。只记住“KV 压缩”而不理解“矩阵吸收”，就没有读懂 MLA 的推理优化。

四项核心贡献

  1. MLA：通过低秩 Key-Value 联合压缩，缓存 latent vector，而不是缓存每个 head 的完整 K/V。
  2. Matrix Absorption：利用线性代数重排，将 Key 上投影吸收到 Query，将 Value 上投影合并到输出侧，避免在每个历史 token 上重建 K/V。
  3. DeepSeekMoE：细粒度专家划分 + 共享专家隔离，提高专家专业化并减少知识冗余。
  4. 通信与负载控制：Device-limited Routing 限制单 token 触达的设备数，再通过 Expert / Device / Communication 三类辅助损失平衡负载。

论文来源：DeepSeek-V2, Abstract 与 Sections 2–3。

02 · Motivation

背景与动机：两个不同的瓶颈

推理侧：KV Cache 随上下文增长

标准 MHA 每个 token、每层需要缓存所有 attention heads 的 K 和 V。上下文越长、并发请求越多，KV Cache 越容易成为显存容量和带宽瓶颈。

MLA 解决

训练侧：稠密 FFN 计算成本高

大模型若每个 token 都经过全部 FFN 参数，计算成本会随总参数量增长。MoE 通过条件计算只激活少数专家，但引入路由与跨设备通信成本。

DeepSeekMoE 解决

为什么不是直接使用 MQA / GQA？

MQA 和 GQA 通过减少 KV heads 降低缓存量，但它们直接减少了 Key/Value 的独立表示数量。DeepSeek-V2 的出发点是：尽量保留多头注意力的表达能力，同时改变 KV 的存储表示——先联合压缩，再在计算时利用矩阵结合律绕开显式恢复。

关键区分：MLA 不是简单把多个 head 合并成一个 KV head。它让不同 head 共享一个低维 KV latent，再通过每个 head 对应的上投影矩阵恢复其 K/V 语义；Matrix Absorption 则让推理时可以不显式执行这次恢复。

04 · Multi-Head Latent Attention

MLA：低秩 Key-Value 联合压缩

4.1 从标准 MHA 开始

令输入 hidden state 为 $h_t\in\mathbb{R}^{d}$，注意力头数为 $n_h$，每头维度为 $d_h$。标准 MHA 通过三个投影得到 Q、K、V：

Standard MHA
$$q_t=W^Qh_t,\qquad k_t=W^Kh_t,\qquad v_t=W^Vh_t.$$ $$o_{t,i}=\sum_{j\le t}\operatorname{Softmax}_j\left(\frac{q_{t,i}^{T}k_{j,i}}{\sqrt{d_h}}\right)v_{j,i}.$$

推理时，每层每 token 需要存储所有 heads 的 K 和 V，因此 KV Cache 元素数为：

$$M_{\mathrm{MHA}}=2n_hd_h\quad\text{(每层、每 token)}.$$

4.2 MLA 的核心：先压缩，再按 head 展开

MLA 不直接生成每个 head 的 Key 和 Value，而是将二者共同映射到一个低维 latent vector：

论文公式 (9)–(11)：Low-Rank KV Joint Compression
$$c_t^{KV}=W^{DKV}h_t,\qquad c_t^{KV}\in\mathbb{R}^{d_c}.$$ $$k_t^C=W^{UK}c_t^{KV},\qquad v_t^C=W^{UV}c_t^{KV}.$$

其中 $W^{DKV}$ 是 down-projection，$W^{UK}$ / $W^{UV}$ 分别是 Key / Value 的 up-projection。关键在于：推理时缓存的是 $c_t^{KV}$，而不是展开后的 $k_t^C$ 和 $v_t^C$。

直观理解：把“每个 head 各自保存一份 K/V”改成“所有 heads 共用一份压缩 latent，再由各自的投影矩阵读取”。压缩本身降低缓存容量；接下来的矩阵吸收则进一步避免推理时把 latent 展开成完整 K/V。

4.3 Query 也做低秩压缩

论文同时压缩 Query，主要目的是降低训练过程中的 activation memory；它本身并不减少 KV Cache。

$$c_t^Q=W^{DQ}h_t,\qquad q_t^C=W^{UQ}c_t^Q.$$ $$c_t^Q\in\mathbb{R}^{d'_c},\quad d'_c\ll n_hd_h.$$

注意：KV 压缩和 Query 压缩的收益不同。$c^{KV}$ 决定推理缓存大小；$c^Q$ 主要影响 Query 投影和训练激活开销。

05 · Matrix Absorption

Matrix Absorption：为什么可以不显式恢复 K/V？

这部分是全文最值得手推的内容。矩阵吸收的本质是：将原本发生在历史 token 上的 KV up-projection，利用矩阵结合律重排到当前 Query 和最终输出路径。

5.1 Key 侧吸收：把 $W^{UK}$ 移到 Query 路径

先只看第 $i$ 个 head 的内容 Key（暂时不考虑 RoPE）。对于历史 token $j$：

$$k_{j,i}^{C}=W_{UK,i}c_j^{KV}.$$ $$s_{t,j,i}=(q_{t,i}^{C})^Tk_{j,i}^{C} =(q_{t,i}^{C})^TW_{UK,i}c_j^{KV}.$$

利用 $(AB)^T=B^TA^T$，把矩阵乘法重新结合：

Key-side Absorption
$$s_{t,j,i}=\underbrace{(W_{UK,i}^{T}q_{t,i}^{C})}_{\widetilde q_{t,i}\in\mathbb{R}^{d_c}}{}^{T}c_j^{KV}.$$ $$\boxed{\widetilde q_{t,i}=W_{UK,i}^{T}q_{t,i}^{C}}$$

这样，Attention 的 QK 点积就变成：

$$s_{t,j,i}=\widetilde q_{t,i}^{T}c_j^{KV}.$$

原先每个历史 token 都需要先执行 $c_j^{KV}\rightarrow k_{j,i}^{C}$；现在每个当前 Query 只需变换一次，之后直接与缓存的 latent $c_j^{KV}$ 做点积。历史 Key 不必逐 token 展开。

5.2 再把吸收矩阵并入 Query 的低秩投影

因为 $q_{t,i}^{C}=W_{UQ,i}c_t^Q$，所以：

$$\widetilde q_{t,i}=W_{UK,i}^{T}W_{UQ,i}c_t^Q.$$ $$\boxed{\widetilde W_{UQ,i}=W_{UK,i}^{T}W_{UQ,i}}$$

推理实现可以把 $W_{UK,i}^{T}$ 与 $W_{UQ,i}$ 预先合并为一个等价的 Query 投影矩阵。每个 decode step 不必先恢复完整 $q_i^C$ 再乘 $W_{UK,i}^{T}$，而是直接得到 latent-space query。

5.3 Value 侧吸收：先做加权求和，再恢复输出

Attention 权重记为 $a_{t,j,i}$。标准 Value 路径为：

$$o_{t,i}=\sum_j a_{t,j,i}v_{j,i}^{C} =\sum_j a_{t,j,i}W_{UV,i}c_j^{KV}.$$ $$=W_{UV,i}\left(\sum_j a_{t,j,i}c_j^{KV}\right).$$

令 latent-space 的加权结果为 $z_{t,i}=\sum_j a_{t,j,i}c_j^{KV}$，则：

$$o_{t,i}=W_{UV,i}z_{t,i}.$$ $$u_t=W^O[W_{UV,1}z_{t,1};\ldots;W_{UV,n_h}z_{t,n_h}].$$

由于 $W^O$ 也是线性变换，可以在代数上把各 head 的 $W_{UV,i}$ 与 $W^O$ 合成一个等价输出矩阵：

$$\boxed{\widetilde W^O=W^O\operatorname{BlockDiag}(W_{UV,1},\ldots,W_{UV,n_h})}.$$

因此不需要为每个历史 token 逐个生成完整 Value。实际推理 kernel 可以显式执行 latent 输出到 Value 的投影，也可以把投影融合进输出侧算子；是否物理融合取决于具体后端实现。

5.4 一张表看懂两侧吸收

路径传统计算吸收后的计算避免的工作
Key$c_j^{KV}\to W_{UK,i}c_j^{KV}$，每个历史 token 展开 K$q_{t,i}^{C}\to W_{UK,i}^{T}q_{t,i}^{C}$，Query 映射到 latent 空间不必为历史 token 显式恢复 K
Value先展开每个 $v_{j,i}$，再按注意力权重求和先对 $c_j^{KV}$ 加权求和，再执行 $W_{UV,i}$ / 输出投影不必逐历史 token 显式恢复 V
不要误解为“没有 K/V 计算”。矩阵吸收改变的是计算位置和中间表示：Key 的 up-projection 被吸收到 Query；Value 的 up-projection被推迟到加权求和之后或融合到输出侧。Attention 仍然要计算分数、Softmax 和加权聚合。
06 · Decoupled RoPE

为什么 MLA 必须使用 Decoupled RoPE？

如果直接对压缩后的内容 Key $k^C=W^{UK}c^{KV}$ 施加 RoPE，那么位置相关的旋转矩阵会插入 $W^{UK}$ 与 Query 的矩阵乘法之间。由于 RoPE 矩阵依赖 token 位置，不能像固定权重那样简单预合并。

直接对内容 Key 使用 RoPE 时的结构（示意）
$$q_t^TR_t^TR_jW^{UK}c_j^{KV}.$$

其中 $R_t$、$R_j$ 分别对应 Query 与 Key 的位置旋转。$R_t^TR_j$ 随 $(t,j)$ 变化，无法并入一个固定的 Query 权重。

DeepSeek-V2 将内容通道与位置通道拆开：内容部分不做 RoPE，另建一组较小维度的 Query/Key 专门承载位置信息。

Decoupled RoPE（论文公式 14–19）
$$q_{t,i}=[q_{t,i}^{C};q_{t,i}^{R}],\qquad k_{t,i}=[k_{t,i}^{C};k_t^{R}].$$ $$q_t^R=\operatorname{RoPE}(W^{QR}c_t^Q),\qquad k_t^R=\operatorname{RoPE}(W^{KR}h_t).$$ $$\operatorname{score}_{t,j,i}= \frac{(q_{t,i}^{C})^TW_{UK,i}c_j^{KV}+ (q_{t,i}^{R})^Tk_j^R}{\sqrt{d_h+d_h^R}}.$$

现在内容部分可以继续做矩阵吸收：

$$\operatorname{score}_{t,j,i}= \frac{\widetilde q_{t,i}^{T}c_j^{KV}+ (q_{t,i}^{R})^Tk_j^R}{\sqrt{d_h+d_h^R}}.$$
记忆点：内容 Key 走 latent-space dot product；位置信息走独立 RoPE 子空间。推理缓存因此不是只有 $c^{KV}$，还必须保存共享的 $k^R$。

08 · DeepSeekMoE

DeepSeekMoE：细粒度专家 + 共享专家

DeepSeekMoE 的两个关键思想：

  1. Fine-grained Expert Segmentation：把专家切得更细，增加组合与专业化空间。
  2. Shared Expert Isolation：隔离少量共享专家，吸收不同 token 之间共通的知识，降低 routed experts 重复学习相同知识的冗余。

8.1 一个 token 的 FFN 输出

$$h'_t=u_t+ \sum_{i=1}^{N_s}\operatorname{FFN}^{(s)}_i(u_t)+ \sum_{i=1}^{N_r}g_{i,t}\operatorname{FFN}^{(r)}_i(u_t).$$ $$s_{i,t}=\operatorname{Softmax}_i(u_t^Te_i),\qquad g_{i,t}=\begin{cases}s_{i,t},&i\in\operatorname{TopK}(s_t,K_r),\\0,&\text{otherwise.}\end{cases}$$

符号说明：$N_s$ 为共享专家数，$N_r$ 为 routed experts 数，$K_r$ 为每个 token 激活的 routed experts 数，$e_i$ 是第 $i$ 个专家的 centroid / router 向量，$s_{i,t}$ 是 token 对专家的 affinity。

8.2 DeepSeek-V2 的实际配置

2Shared Experts
160Routed Experts
6每 token 激活 routed experts
1536每个专家的 intermediate dim

除第一层 FFN 外，其他 FFN 均替换为 MoE 层。每个 token 会经过 2 个共享专家，并从 160 个 routed experts 中选择 6 个。总参数量为 236B，但每个 token 只激活约 21B 参数。

09 · Device-limited Routing

Device-limited Routing：限制的是设备数，不是专家数

细粒度专家增加了每个 token 的可选专家数。如果 Top-K 专家分布在很多设备上，token 的 hidden states 就需要被发送到更多设备，MoE 的 All-to-All 通信可能成为瓶颈。

流程是：

  1. 先计算 token 对 routed experts 的 affinity scores。
  2. 先选出拥有高 affinity experts 的 $M$ 个设备。
  3. 只在这 $M$ 个设备所承载的 experts 中执行 Top-K。
符号含义DeepSeek-V2 训练配置
$D$设备 / 专家组数量8
$M$每个 token 最多触达的设备数3
$K_r$每个 token 激活的 routed experts 数6
论文的经验观察：当 $M\ge3$ 时，device-limited routing 的效果大致可以与不限制设备的 Top-K routing 对齐。这里 $M=3$ 是设备数上限，$K_r=6$ 是专家数，二者不要混淆。
10 · Load Balancing

三类负载均衡损失：Expert / Device / Communication

论文明确指出，负载不均衡会导致两类问题：一是部分专家被过度选择、部分专家训练不足，产生 routing collapse；二是 EP 设备之间的计算和通信不均，降低整体吞吐。

10.1 Expert-level Balance

先约束专家维度上的 token 分配。令 $T$ 为统计窗口中的 token 数，$f_i$ 是专家 $i$ 的归一化实际负载，$P_i$ 是 router 给专家 $i$ 的平均概率：

$$\mathcal L_{\mathrm{ExpBal}}= \alpha_1\sum_{i=1}^{N_r}f_iP_i.$$ $$f_i=\frac{N_r}{K_rT}\sum_{t=1}^{T} \mathbb{1}(\text{token }t\text{ selects expert }i),$$ $$P_i=\frac{1}{T}\sum_{t=1}^{T}s_{i,t}.$$

直觉：如果一个专家已经接收了大量 token，同时 router 仍给它很高的平均概率，那么乘积项就会变大。损失鼓励实际负载和 router 概率不要长期集中到少数专家。

10.2 Device-level Balance

将 routed experts 分成 $D$ 个组，每组部署在一个设备上。对设备 $d$，汇总该设备所含专家的平均负载和路由概率：

$$\mathcal L_{\mathrm{DevBal}}= \alpha_2\sum_{d=1}^{D}f'_dP'_d.$$ $$f'_d=\frac{1}{|\mathcal E_d|} \sum_{j\in\mathcal E_d}f_j,\qquad P'_d=\sum_{j\in\mathcal E_d}P_j.$$

它解决的是“某张 GPU 上的专家组太忙、另一张 GPU 上的专家组太闲”的计算负载问题。它不等价于 expert-level balance：单个专家均匀，不代表设备间一定均匀。

10.3 Communication Balance

Device-limited routing 约束了每个 token 的发送范围，但某设备仍可能接收远多于其他设备的 token。因此论文额外定义接收通信负载：

$$\mathcal L_{\mathrm{CommBal}}= \alpha_3\sum_{d=1}^{D}f''_dP''_d.$$ $$f''_d=\frac{D}{MT}\sum_{t=1}^{T} \mathbb{1}(\text{token }t\text{ is sent to device }d),$$ $$P''_d=\sum_{j\in\mathcal E_d}P_j.$$

论文给出的目标是：在发送端，每个设备最多发送约 $MT$ 个 hidden states；同时通过通信均衡损失，鼓励每个设备接收的 hidden states 也在约 $MT$ 的量级。

10.4 三类损失分别在平衡什么？

损失统计对象主要防止不均衡后果
ExpBal单个 expert专家路由塌缩部分专家过载、部分专家欠训练
DevBal设备上的专家组计算负载不均GPU 间计算时间不一致

论文还使用 device-level token dropping：先按每个设备的平均计算预算设置 capacity factor = 1.0，再在设备内丢弃 affinity 最低的 token，直到满足预算；约 10% 的训练序列被设置为永不丢 token。评估时不丢 token。

Data Parallelism：使用 ZeRO-1。论文称无需 Tensor Parallelism。

训练系统基于内部 HAI-LLM 框架。论文还提到：共享专家计算与 EP All-to-All 通信重叠；为通信、路由和跨专家融合线性层定制 CUDA kernel；MLA 基于改进版 FlashAttention-2 优化。

硬件为 NVIDIA H800 集群：单节点 8 GPU，节点内使用 NVLink / NVSwitch，跨节点使用 InfiniBand。

13 · CP Research Connection

MLA 与 Context Parallelism：如何连接两条研究线？

这一节是基于论文公式与公开推理框架源码做的工程延伸分析，不是 DeepSeek-V2 原论文提出的 CP 算法。

13.1 先把 EP 与 CP 分开

并行方式切分对象主要通信DeepSeek-V2 论文中的角色
EP专家集合 / expertstoken dispatch / combine，常见 All-to-All明确使用 8-way EP

PPTransformer layerspipeline stage 间激活传递使用 16-way PP

13.2 MLA 对 CP 的潜在收益

如果 CP rank 之间传输的是 MLA 的压缩缓存，而不是展开后的多头 K/V，那么每个 token 的 KV payload 理论上可从 $2n_hd_h$ 个元素降到 $d_c+d_h^R$ 个元素。DeepSeek-V2 的对应数值是 32768 → 576。

$$\text{MHA KV payload/token/layer}=2n_hd_h=32768,$$ $$\text{MLA latent payload/token/layer}=d_c+d_h^R=576.$$

但这不意味着 CP 通信消失。跨 CP 分片计算全局 attention 时，仍需要正确合并不同分片的 softmax 归一化统计量（例如 max / sum-exp 或 LSE）以及加权 Value 部分结果。MLA 主要压缩被传输或缓存的 K/V 表示，并不改变 attention 对全局上下文的依赖。

13.3 一个值得验证的 CP + MLA 计算流程

  1. 每个 CP rank 保存本地 token 的 $c^{KV}$ 与 $k^R$。
  2. Query 经过 Key-side absorption，得到 latent-space query。
  3. 分片 attention 计算局部 logits / 局部统计量，并做全局 softmax 合并。
  4. 对 latent Value 加权结果做 Value up-projection，再完成输出投影。
研究中的关键 trade-off：latent cache 很小，但每个 head 的 latent Value 维度是 $d_c$，比常规 $d_v$ 大。CP 设计不能只看 KV cache bytes，还要同时测量 partial output / LSE 合并开销、Query 复制或聚合开销，以及 Value projection 放在 reduce 前还是 reduce 后的通信量。

13.4 公开实现中可观察到的 CP / DCP 线索

  • vLLM MLA：代码将 `kv_c_normed` 与 `k_pe` 作为 latent cache 输入，并提供 PCP/DCP 管理路径；可查看 KV cache update 与 MLA DCP manager。
  • SGLang MLA：当前实现包含 DCP decode / extend 分支；可查看 DCP extend KV gather、decode / extend 的 DCP 分支。

术语提示：这里的 DCP 通常指 Decode Context Parallelism，PCP 指 Prefill Context Parallelism。它们是推理系统中的上下文并行实现，不应直接等同于原论文训练并行配置。公开代码随版本演进，阅读时请固定 commit。

15 · Critical Reading

易混淆点与论文边界

  1. 低秩压缩 ≠ 矩阵吸收。低秩压缩把 K/V 表示变成 latent；矩阵吸收让推理计算不必显式恢复完整 K/V。两者协同，但不是同一件事。
  2. Query 压缩不是 KV Cache 压缩。$c^Q$ 的主要收益是降低训练激活内存；缓存大小主要由 $c^{KV}$ 与 $k^R$ 决定。
  3. RoPE 不是简单地“照常加上去”。若把 RoPE 施加在被 $W^{UK}$ 展开的内容 Key 上，位置矩阵会妨碍固定矩阵吸收，因此论文采用 decoupled RoPE。
  4. 93.3% 不是 98.24%。前者是相对 DeepSeek 67B 的部署指标；后者是按 128-head MHA 元素数计算的理论对照。
  5. Device-limited routing 不等于 load balancing。前者限制每个 token 触达的设备范围；三类 auxiliary losses 进一步控制专家、设备和通信负载。
  6. EP 不等于 CP。EP 切分专家并路由 token；CP 切分序列并分布式计算 attention。DeepSeek-V2 原论文报告 8-way EP、16-way PP、ZeRO-1 DP，没有提出训练 CP 算法。
  7. 不要把推理代码当训练代码。公开 serving repo 能追踪 Top-K、dispatch、combine 和 MLA kernel，但不代表论文中所有训练辅助损失和 token dropping 的实现细节都已公开。
16 · Further Research

下一步值得验证的研究问题

Matrix Absorption / Kernel

  • 在 prefill 和 decode 两个阶段，何时选择 compute-friendly MHA，何时选择 data-movement-friendly latent MQA？阈值与 $S_q/S_{kv}$、batch size、KV length 如何相关？
  • 把 $W_{UK}^{T}$ 融入 Query projection 后，BMM 的 shape、内存布局和 head parallel 方式如何变化？
  • Value 侧的 $W_{UV}$ 是独立 BMM、融合到 $W_O$，还是在 CP reduce 后执行？不同选择如何影响通信量和算力？
  • FP8 / INT8 / BF16 下，吸收矩阵的预合并与量化顺序是否影响数值误差？

CP / DCP

  • CP rank 之间究竟传输 latent $c^{KV}+k^R$，还是已经展开的 K/V？实际 bytes/token/layer 是多少？
  • 跨分片 softmax 的 max、sum-exp / LSE 与 partial output 如何合并？通信能否与本地 latent attention overlap？
  • 若 Value latent 维度 $d_c=512$ 大于 $d_v=128$，将 $W_{UV}$ 放在跨 rank reduce 前或后，哪种布局更优？
  • Prefill CP 与 Decode CP 的瓶颈不同：prefill 更关注长序列并行与 chunked attention，decode 更关注 KV 读取、通信延迟与 batch 并发。

MoE / EP

  • Expert、Device、Communication 三种损失之间是否存在梯度冲突？不同 $\alpha$ 如何改变专家利用率、设备吞吐与 token drop rate？
  • Device-limited routing 的 $M$ 从 1 增加到 8 时，质量、All-to-All bytes、设备热点和尾延迟如何变化？
  • 在 CP + EP 混合并行中，token dispatch 的通信拓扑如何与 context attention 的通信拓扑竞争网络带宽？
